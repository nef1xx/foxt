# Голосование BRATKI 2026

## Состав

- `vote.html` — ник + личный код, выбор двух дополнительных номинаций на первом этапе или кандидатов на втором, проверка и отправка целого бюллетеня, общие результаты.
- `admin.html` — настройка восьми номинаций, запуск первого этапа на 72 часа, выдача и перевыпуск кодов, явка, закрытие и публикация.
- `voting-config.js` — только URL Supabase RPC и **publishable** key. Пустая конфигурация показывает подготовку и не принимает голоса.
- `supabase/migrations/202611070001_voting.sql` — настоящая серверная логика PostgreSQL.

GitHub Pages обслуживает интерфейс. База, проверка личных кодов и подсчёт работают в отдельном проекте Supabase. Дополнительные номинации выбирают участники. Кандидатов задаёт организатор перед открытием второго этапа.

## Развёртывание в новом проекте Supabase

1. Подключить Supabase к чату и создать отдельный проект BRATKI. Не применять миграцию к чужой рабочей базе.
2. Применить миграции `supabase/migrations/202611070001_voting.sql`, затем `supabase/migrations/202611100001_extra_nomination_vote.sql` через управление проектом. Для уже подключённого проекта нужна только вторая миграция. `pgcrypto` используется в схеме `extensions`.
3. Выполнить `node scripts/prepare-voting-admin.mjs` один раз, если `.private/production-admin.txt` ещё не существует. Скрипт откажется случайно менять уже созданный ключ.
4. Выполнить содержимое `.private/bootstrap-admin.sql` через привилегированное управление Supabase. Оно задаёт только хеш ключа организатора; браузерные пользователи сделать это не могут.
5. Указать в `voting-config.js`:

```js
window.BRATKI_VOTING = {
  apiUrl: 'https://<project-ref>.supabase.co/rest/v1/rpc',
  publishableKey: 'sb_publishable_...',
};
```

6. Проверить доступность пяти RPC (включая `bratki_submit_extras`) через publishable key, недоступность приватных таблиц и вход с ключом организатора. Вызовы выполняются POST-запросами с ключом проекта в заголовке `apikey`.
7. Выполнить `npm run check`, `npm test`, `npm run build` и опубликовать обновление GitHub Pages.

Приватный ключ организатора находится в `.private/production-admin.txt`. Личные коды участников **не генерируются заранее** и не коммитятся. Папка `.private/`, локальная база и `.env` исключены из Git. Сборка копирует только перечисленные публичные файлы, изображения и шрифты. Она отклоняет настройку с secret/service-role ключом или локальным API.

## Действия организатора

1. Открыть `/admin.html`, ввести ключ организатора.
2. Добавить ники участников, по одному в строке. Нажать «Выдать личные коды», скачать приватный TXT и отправить каждому **только его ник и код**. Код нужно сохранить для обоих этапов.
3. Нажать «Открыть первый этап · 3 дня». С этого момента у всех единый срок в 72 часа. Перезагрузка страницы, смена устройства и повторное нажатие не перезапускают таймер. Участников можно добавлять до начала второго этапа.
4. На первом этапе каждый выбирает ровно две разные дополнительные номинации из четырёх. Один код принимается один раз на этом этапе. Счётчики номинаций скрыты до дедлайна даже в панели организатора.
5. После дедлайна сервер отклоняет новые голоса. При следующем обращении к API он фиксирует итоги: две номинации с наибольшим количеством голосов проходят дальше. При равенстве действует порядок «Завоз», «Смешной», «Сердце», «Мудрость»; при отсутствии голосов применяется то же правило. Об этом сообщается участникам до отправки голоса. Расписание или открытая вкладка для соблюдения дедлайна не нужны.
6. Добавить минимум двух кандидатов в каждую из шести активных номинаций и сохранить состав. Выбранные участниками номинации вручную не меняются. Нажать «Открыть голосование» для второго этапа: теперь кандидаты и список участников заморожены. Тот же личный код работает для нового бюллетеня; участие на первом этапе не обязательно для второго.
7. Отслеживать явку по текущему этапу и отметку о выборе номинаций. Выгрузка явки содержит обе отметки. Точное время отправки и индивидуальный выбор не сохраняются. Потерянный код можно перевыпустить, если участник ещё не голосовал на текущем этапе.
8. Закрыть голосование за кандидатов, проверить общие итоги и отдельно нажать «Опубликовать итоги». Сброс голосов и повторный запуск первого этапа из панели не предусмотрены.

До закрытия даже обычная панель организатора не возвращает счётчики кандидатов. Это ограничивает возможность связать изменение результата с последним проголосовавшим. После публикации результаты доступны участникам общей суммой, с процентами и корректным отображением ничьей.

## Проверки и локальная разработка

```sh
npm ci
npm run check
npm test
npm run dev:voting
```

Локальный режим работает на `http://127.0.0.1:4180/`, использует настоящий PostgreSQL через PGlite и те же SQL-функции, что Supabase. Локальная БД сохраняется в `.private/voting-dev/`, отдельный ключ организатора — в `.private/dev-admin.txt`. Это **не** приём публичных голосов. Конфигурация локального API выдаётся только dev-сервером и не попадает в `dist/`.

Тесты проверяют права `anon`, отсутствие доступа к приватным таблицам, неизменяемость открытого состава, привязку кода к нику, хеширование кодов, отклонение неполных и неверных бюллетеней без расходования кода, повторную/конкурентную доставку без удвоения счётчиков, перевыпуск, закрытие и публикацию. PGlite работает в одном процессе; реальная многосессионная конкуренция в облаке дополнительно защищена блокировкой строки сезона PostgreSQL.

## Границы защиты

- Один код — один бюллетень на каждом этапе, проверка и подсчёт выполняются одной транзакцией PostgreSQL. При потерянном ответе повторная отправка возвращает подтверждение предыдущего приёма.
- Код состоит из 96 случайных бит, привязан к нормализованному нику; в базе хранится SHA-256, исходные коды не выдаются повторно.
- У приватных таблиц включён RLS и отозваны права `public`, `anon`, `authenticated`. API публикует только ограниченные функции с явными проверками и пустым `search_path`.
- В приложении нет таблицы индивидуальных бюллетеней или связки «участник → выбор»: есть участники с отметками и отдельные агрегированные счётчики. Нет времени отправки у участника. Содержимое выбора не отправляется в аналитику или console.
- Это не криптографическая анонимность от владельца инфраструктуры. Привилегированный доступ, журналы запросов и история изменений базы могут позволить восстановление. Supabase-инфраструктуру следует доверять организатору; защита от DDoS не заявляется.
- Личные коды — предъявительские секреты: передавший свой код другому человеку передаёт возможность проголосовать. Организатор контролирует выдачу и не должен выдавать одному человеку несколько ников.
